Mode d’emploi

Comment lire ces architectures

Chaque schéma décrit un mécanisme, pas une règle isolée. Si deux templates partagent le même jugement (Gemini cabin, fusion identité, géométrie zone…), ils partagent le même schéma — seules changent la condition rules-engine et le packaging d’alerte.

1. Signal

Qui voit l’objet ? En général Frigate (person/car) ou le moteur local (qualité vidéo).

2. Jugement

Qui décide l’événement métier ? Géométrie, vitesse Frigate, Gemini, InsightFace, OCR, ou composite.

3. Règle

Le rules-engine ne détecte pas : il matche event_type + bindings caméra/zone/liste.

4. Preuve

Clip ~6 s + images (scène / sujet / face / plaque). Fail-closed si artefact manquant exigé.

Partie A

Dix architectures de règles

Ces dix patterns couvrent le catalogue. Les badges catalogue real / partial / beta restent la vérité produit : un schéma « beau » ne transforme pas une règle partial en DoD.

A1 · Archetype face

Identité faciale — fusion à priorité

Frigate détecte une personne et livre un crop. Trois votes indépendants (Frigate Face Library, InsightFace vs watchlist, Gemini multimodal sur photos d’enrôlement) sont fusionnés. Priorité : Frigate > InsightFace > Gemini. Fail-closed : pas de match inventé. En UI, « liste noire » = liste face_watchlist → event face_watchlist_match (pas de type DB séparé). 

flowchart LR
  F[Frigate person] --> C[crop JPEG]
  C --> V1[Frigate Face]
  C --> V2[InsightFace watchlist]
  C --> V3[Gemini refs]
  V1 --> Fuse[fusion priorité]
  V2 --> Fuse
  V3 --> Fuse
  Fuse -->|match+label| M[face_watchlist_match]
  Fuse -->|visage sans match| U[face_unknown]
  Fuse -->|audit| D[face_detected]
  M --> R[rules-engine]
  U --> R
  D --> R
  R --> E[clip 6s + scene + face bbox]

Même fonctionnement

tpl-face-watchlist tpl-watchlist-match tpl-face-detected tpl-unknown-face

Combine avec

tpl-identity-correlation
  • Corrélation face + plaque dans une fenêtre (A10).

Preuves

  • Clip 6 s + image scene (full) + image face (bbox).
  • Fail-closed sur le rôle face. Métadonnées utiles : face_label, identity_votes, identity_winner.

Debug pragmatique : watchlist active + photos enroll + Frigate face ON + crop lisible. Si face_enqueued=0, le bridge ne voit pas de person utile — ce n’est pas encore Gemini.

A2 · Archetype cabin

Cabin Gemini — jugement yes / no

Frigate signale un véhicule dans une zone à behavior cabin (seatbelt, téléphone…). Un crop (souvent vehicle_bbox) part dans la file VLM. Gemini répond violation ou non. Fail-closed : pas de violation claire → cabin_ignored, aucun event, donc aucune alerte (ce n’est pas un « rejet de crop »). 

flowchart LR
  F[Frigate car zone cabin] --> C[crop vehicle_bbox]
  C --> Q[VLM queue]
  Q --> G[Gemini judge]
  G -->|violation=true| E1[seatbelt_violation / phone_usage]
  G -->|no / unclear| X[cabin_ignored fail-closed]
  E1 --> R[rules-engine]
  R --> Ev[clip 6s + scene + subject]

Même fonctionnement

tpl-seatbelt tpl-phone-driving

Ne pas confondre

  • A4 feu : signal HSV + véhicule, pas habitacle.
  • A3 vitesse : jugement numérique, pas VLM yes/no.

Debug : spatial seatbelt chaud → cabin_enqueued>0 → vlm_completed. Si emitted=0 et rejected=0, Gemini a souvent répondu « pas de violation ».

A3 · Archetype measure

Vitesse — pont Frigate speed

Le track Frigate + zone/ligne de mesure produisent une estimation speed_kmh. Comparaison au seuil (règle / zone). Au-dessus → event speeding. Preuve : scène + sujet + plaque si le pipeline plaque est branché. 

flowchart LR
  F[Frigate track + zone speed] --> S[estimate speed_kmh]
  S -->|above limit| Evt[speeding]
  S -->|below| Drop[speed_below_limit]
  Evt --> R[rules-engine]
  R --> Ev[clip 6s + scene + subject + plate?]

Même fonctionnement

tpl-speeding tpl-speeding-premium variantes vitesse

Combine avec

tpl-speeding-premium tpl-plate-detected
  • Vitesse canonique + plaque en règles séparées (plus de traffic-pipeline).

Debug : zone speed_measurement en spatial AI + bridge speed ON. Compteurs speed_emitted vs speed_below_limit.

A4 · Archetype dual_signal

Feu rouge — géométrie + état feu

Deux signaux doivent s’aligner : véhicule dans la zone d’observation et feu jugé rouge (HSV / état stable, éventuellement vote Gemini). Sinon skip explicite (skipped_not_red). C’est le pattern « dual signal », plus exigeant qu’une simple présence zone. 

flowchart LR
  F[Frigate car ∩ zone] --> H[HSV / light state]
  F --> C[crop]
  C --> G[Gemini vote optionnel]
  H --> J[jugement geometry ± VLM]
  G --> J
  J -->|red + cross| Evt[red_light_violation]
  J -->|not red| Skip[skipped_not_red]
  Evt --> R[rules-engine]
  R --> Ev[clip 6s + scene + subject + plate]

Même fonctionnement

tpl-red-light

Preuves typiques

  • Clip 6 s, scène, sujet véhicule, plaque si dispo.
  • Métadonnées feu (état HSV / vote) dans le package.

Debug : zone feu + behavior traffic light en spatial. Distinguer « pas de voiture » vs « feu pas rouge » vs « Gemini refuse ».

A5 · Archetype geometry

Géométrie de zone — présence, durée, périmètre

Frigate (ou moteur local) fournit tracks/objets. Le jugement est spatial-temporel : entrée zone, présence, loitering / dwell, arrêt, absence, franchissement de périmètre. Pas de VLM obligatoire. La zone doit être active et liée à la caméra (jamais hardcodée). 

flowchart LR
  F[Frigate object in zone] --> G[geometry engine]
  G -->|enter/present| P[zone_enter / presence]
  G -->|dwell/loiter| L[loitering / dwell]
  G -->|breach| B[perimeter_breach]
  G -->|stopped| St[person/vehicle_stopped]
  G -->|absence| A[zone_absence]
  P --> R[rules-engine]
  L --> R
  B --> R
  St --> R
  A --> R
  R --> Ev[clip 6s + scene + subject]

Même fonctionnement

tpl-zone-presence tpl-zone-absence tpl-loitering tpl-loitering-entrance tpl-perimeter-breach tpl-dwell-exceeded tpl-person-stopped tpl-vehicle-stopped

Variante quality (flou / obscurité) : même idée « jugement local », mais signal citevision_local plutôt que Frigate.

Debug : zone dans Frigate (cv_zone_*) + spatial AI. Puis event géométrie avant d’accuser la règle.

A6 · Archetype line

Ligne — croisement & franchissement

Une ligne (pas une zone) découpe le plan. Le track Frigate qui la traverse émet line_cross (éventuellement filtré par direction / classe). Sert au comptage directionnel et aux interdictions de franchissement de ligne (tpl-line-cross-forbidden). Le sens interdit routier est un autre pattern (A6b). 

flowchart LR
  F[Frigate track] --> L[line geometry]
  L -->|cross| Evt[line_cross]
  Evt --> R[rules-engine]
  R --> Ev[clip 6s + scene + subject]

Même fonctionnement

tpl-line-cross tpl-line-cross-bidir tpl-line-cross-forbidden

Lien avec A7

  • Les agrégats peuvent compter des crossings dans une fenêtre temporelle.

Debug : ligne active en DB + présente côté spatial/Frigate. Une cam « ligne seule » n’active pas forcément les gates cabin/live — autre sujet (ingest).

A6b · Sens interdit (zone)

Sens interdit — arêtes entrée / sortie

Zone polygone (4+ points) avec entry_edge_index et exit_edge_index. Sens autorisé = entrer par l’arête d’entrée et sortir par l’arête de sortie. Le chemin inverse émet wrong_way (tpl-wrong-way) via bridge Frigate ou géométrie locale (XOR FRIGATE_GEOMETRY_BRIDGE). 

flowchart LR
  Z[zone wrong_way + edges] --> E[enter nearest edge]
  E --> X[exit nearest edge]
  X -->|not entry to exit| W[wrong_way]
  W --> R[tpl-wrong-way + evidence]

Catalogue

tpl-wrong-way tpl-wrong-lane → redirect tpl-wrong-direction → redirect

Debug : behavior zone wrong_way, deux arêtes distinctes, track véhicules Frigate, event wrong_way à la sortie.

A7 · Archetype aggregate

Agrégats — seuils & densité

On ne juge pas un individu « en faute », on agrège (count, densité, fenêtre). Quand le seuil est franchi → event de seuil. Utile pour foule, files, parking saturé. 

flowchart LR
  F[Frigate objects] --> C[count / density window]
  C -->|threshold| Evt[vehicle_count / crowd_*]
  Evt --> R[rules-engine]
  R --> Ev[clip 6s + scene]

Même fonctionnement

tpl-vehicle-count tpl-crowd-count tpl-crowd-density

Combine avec

observation N/OR

Debug : vérifier la fenêtre de comptage et le seuil dans les bindings — souvent un faux « bug IA » est un seuil trop haut.

A8 · Archetype plate

Plaque — OCR fusion + listes

Crop véhicule/plaque → PaddleOCR (+ Gemini OCR optionnel) → fusion texte. Puis politique de liste : plate_block, allow, unknown, repeat. Listes plaque ≠ watchlist visage (types DB distincts). 

flowchart LR
  F[Frigate vehicle] --> C[plate crop]
  C --> O1[PaddleOCR]
  C --> O2[Gemini OCR?]
  O1 --> Fuse[ocr_fusion]
  O2 --> Fuse
  Fuse --> Det[plate_detected]
  Det --> List{listes}
  List -->|block| Bl[plate_blocked]
  List -->|allow| Wh[whitelist logic]
  List -->|unknown| Un[plate_unknown]
  List -->|repeat| Rep[plate_repeat]
  Det --> R[rules-engine]
  Bl --> R
  Un --> R
  Rep --> R
  R --> Ev[clip 6s + scene + plate]

Même fonctionnement

tpl-plate-detected tpl-blocked-plate tpl-plate-whitelist tpl-unknown-plate tpl-plate-repeat

Combine avec

A1 face A3 speed A4 red light

Debug : OCR health + crop lisible. Blocklist active. Pour routier DoD, plaque souvent exigée dans le package preuve.

A9 · Archetype objects

Objets — abandon, retrait, disparition

Pattern géométrie + temps sur un objet (sac, valise…). Signal souvent hybrid (Frigate + logique locale). Différent du loitering personne (A5) par la classe objet et la durée d’abandon. 

flowchart LR
  F[Frigate / hybrid object] --> G[geometry + time]
  G -->|left behind| Ab[object_abandoned]
  G -->|removed| Rm[object_removed]
  Ab --> R[rules-engine]
  Rm --> R
  R --> Ev[clip 6s + scene + object bbox]

Même fonctionnement

tpl-abandoned-object tpl-object-removed tpl-object-disappeared → redirect

Debug : durée minimale d’abandon / disparition dans les bindings. Souvent trop courte en démo, trop longue en prod.

A10 · Archetype composite

Composite — séquence d’atomes déjà prouvés

Pas un nouveau détecteur. Le rules-engine attend plusieurs atoms (ex. face + plaque, vitesse + feu) dans une fenêtre. Preuve = union des packages. Si un atom a evidence_status=missing, le composite se tait (fail-closed). 

flowchart LR
  A1[atom A + evidence] --> W[window / sequence]
  A2[atom B + evidence] --> W
  W -->|all OK| Comp[composite match]
  W -->|missing evidence| Fail[suppress fail-closed]
  Comp --> R[alert composite]
  R --> Ev[union des preuves]

Même fonctionnement

tpl-identity-correlation tpl-industrial-intrusion Compteur scénario N/OR intrusion + schedule tpl-traffic-pipeline → redirect

Les composites restent partial tant que chaque atom n’a pas son DoD individuel.

Debug : valider d’abord chaque atom isolément (validate_rule). Un composite ne répare jamais un atom froid.

Partie B

Six architectures produit

Au-delà des règles : comment la plateforme démarre, se soigne, orchestre les sorties, onboarde une caméra, fait tourner les containers, et stocke les preuves.

B1 · Runtime

Démarrage Start-CiteVision

Le launcher Windows (messages produit, logs streamés) délègue au runtime WSL. start-full-stack.sh en STRICT enchaîne infra → API → IA → rules → business readiness (spatial / rules / Frigate / go2rtc) → UI → watchdogs. Échec readiness = Start non-zéro (plus de « vert mensonger »). 

flowchart TD
  PS[Start-CiteVision.ps1] --> WSL[WSL runtime]
  WSL --> Env[runtime env LIVE_108=1]
  Env --> Dock[dockerd + compose infra]
  Dock --> API[backend]
  API --> AI[ai-engine]
  AI --> RE[rules-engine]
  RE --> BR[ensure_business_readiness]
  BR --> UI[frontend :5174]
  UI --> Watch[watchdogs]
  BR -->|FAIL| Abort[Start exit non-0]

Pragmatique : un client ne doit voir que « Starting services… » / étapes propres — pas des chemins miroir labo.

B2 · Resilience

Auto-heal global + readiness métier

Deux couches : (1) ports / containers publiés (watch-infra-ports), (2) état métier chaud (watch-business-readiness) — spatial AI, parité rules, clés zones Frigate, streams go2rtc. Probe → heal → re-probe → FAIL ou WARN selon STRICT. 

flowchart TD
  Probe[probe ports / spatial / rules / Frigate / go2rtc] -->|OK| Idle[OK]
  Probe -->|KO| Heal[heal restart / resync / rebuild / repair]
  Heal --> Reprobe[re-probe]
  Reprobe -->|OK| Idle
  Reprobe -->|KO| Fail[FAIL STRICT / WARN soft]
  Watch[watchdogs ~30s] --> Probe

Pragmatique : distinguer « Redis down » (infra) de « zone_count=0 » (métier). Les heals ne sont pas interchangeables.

B3 · Sorties

Orchestration alerte → webhook / mail

Event MQTT → match rules-engine → alerte persistée → composition preuve async → routing (webhook HTTP, mail). Si la politique exige des preuves complètes, pas d’alerte « finale » tant que evidence_status≠complete. 

flowchart LR
  Ev[event MQTT] --> RE[rules-engine match]
  RE --> Al[alert DB]
  Al --> Evd[evidence async]
  Evd -->|complete| Out[routing]
  Out --> WH[webhook]
  Out --> Mail[mail / Mailhog]
  Evd -->|missing| Hold[pas de finale fail-closed]

Pragmatique : tester le webhook avec une alerte déjà complete. Un 200 webhook sur alerte sans clip n’est pas un DoD.

B4 · Onboarding

Ajout d’une caméra

UI → ligne cameras (metadata RTSP / go2rtc) → rebuild Frigate (cv_<uuid>) → orchestrator StartCamera vers l’IA avec spatial. Zones/lignes ensuite via ZoneEditor uniquement (jamais scripts qui réécrivent la géométrie). 

flowchart TD
  UI[UI onboard] --> DB[(cameras)]
  DB --> RTSP[RTSP / go2rtc_src]
  DB --> Frig[Frigate rebuild]
  DB --> Ing[SyncNow StartCamera]
  Ing --> AI[AI spatial + ingest]
  UI --> Zones[ZoneEditor]
  Zones --> Spat[resync-spatial]
  Spat --> AI

Pragmatique : cam en Live View ≠ cam ingérée IA. Vérifier spatial + bridge après ajout de zone/règle.

B5 · Infra

Orchestration des containers

Compose sous dockerd WSL natif (pas Docker Desktop) : Postgres, Redis, Mosquitto, MinIO, go2rtc, Frigate, OCR optionnel. Backend / AI / rules / frontend restent des process host surveillés par watchdogs — pas tout est « un container ». 

flowchart TD
  Compose[docker compose] --> PG[(postgres)]
  Compose --> Redis[(redis)]
  Compose --> MQTT[mosquitto]
  Compose --> Minio[(minio)]
  Compose --> G2[go2rtc]
  Compose --> Fr[frigate]
  Compose --> OCR[ocr?]
  API[backend process] --> PG
  API --> Redis
  AI[ai-engine process] --> MQTT
  AI --> Fr
  RE[rules-engine] --> MQTT
  RE --> API

Pragmatique : ports host morts (6380, 1984…) = symptôme classique après hibernation Windows — heal infra avant de toucher aux règles.

B6 · Données

Preuves — Postgres + MinIO

Events et alerts vivent en Postgres. Les binaires (clip, JPEG scène/sujet/face/plaque) vont dans MinIO. Le composer attend le clip Frigate / alignement temporel ; il ne fabrique pas de preuve de secours. Retention démo purge vieux artefacts. 

flowchart LR
  Det[détection] --> Ev[(events)]
  Ev --> Al[(alerts)]
  Al --> Comp[evidence composer]
  Comp --> Clip[clip 6s]
  Comp --> Img[scene + subject/face/plate]
  Clip --> S3[(MinIO)]
  Img --> S3
  Comp --> Meta[evidence_status]
  Meta --> Al
  Ret[retention] --> S3
  Ret --> Ev

Statuts preuve à connaître

  • complete — package prêt, alerte présentable comme finale.
  • missing — cause loguée (clip_not_ready, scene_green, align_too_large, timeout…).
  • Interdit : fabriquer une plaque / sujet de substitution pour « passer au vert ».

Pragmatique : pour valider une règle, exiger alerte UI + fichiers MinIO + mail si configuré — pas seulement un log MQTT.
